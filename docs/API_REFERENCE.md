# API Reference

Status: pre-alpha package map for `@werhiz/rhiz-harness`. Exact TypeScript declarations generated by the current source are authoritative.

The package is currently private and versioned `0.0.1-kernel.0`. APIs may change before the public open-source release. Portable contract changes should still respect the Constitution and accepted architecture decisions.

## Package entry points

| Import | Purpose |
| --- | --- |
| `@werhiz/rhiz-harness` | portable Harness contracts and modules |
| `@werhiz/rhiz-harness/codex` | Codex App Server adapter |
| `@werhiz/rhiz-harness/dsh` | DSH Host adapter |
| `@werhiz/rhiz-harness/dsh-products` | DSH product worker routes |
| `@werhiz/rhiz-harness/git-worktrees` | Git workspace/candidate adapter |
| `@werhiz/rhiz-harness/local-verify` | local command verification adapter |
| `@werhiz/rhiz-harness/durable-ledger` | durable local Ledger adapter |

The root portable entry point must remain free of DSH and Rhiz Protocol dependencies.

## Portable modules

The root barrel exports the modules below.

### `schemas`

Canonical serializable domain schemas and types.

Important contracts include:

- `ActorRef`
- `ResourceRef`
- `EvidenceRef`
- `AuthorityPolicy`
- `AcceptanceCriterion`
- `EvidenceRequirement`
- `ContextRequest`
- `WorkerPolicy`
- `VerificationPolicy`
- `WorkContract`
- `HarnessEvent`
- Guard request/verdict/evaluation records
- tainted strings and attachments

Prefer the exported parse/schema functions over ad hoc casting at trust boundaries.

### `board`

Deterministic projection of durable Work events into canonical organizational state.

Use Board when you need current Work/Task/Attempt/integration state derived from an event stream. Do not maintain a second mutable Work-state store beside it.

### `ledger`

Portable append/read/replay and audit contracts for durable event storage.

Concrete storage belongs in adapters. The local durable implementation is exported separately through `durable-ledger`.

### `host`

Portable host/provider interfaces and runtime-facing schemas.

Key concepts:

- `HarnessHost`
- `HostCapabilities`
- `WorkerProvider`
- `WorkerDescriptor`
- `WorkerCapabilities`
- `WorkerStartRequest`
- `WorkerStartOptions`
- `WorkerHandle`
- `WorkerObservation`
- `WorkerResult`
- `WorkspaceBinding`
- `requireBoundExecutionRoot`
- host capability consistency validation

`WorkerStartRequest` is serializable. Runtime-only mechanisms such as Guard callbacks belong in `WorkerStartOptions`.

### `workers`

Worker catalog and deterministic capability-aware provider selection.

Use this module to register hosts/providers, discover eligible workers, apply Work preference policy, and obtain typed failure reasons when no provider satisfies the requirements.

### `crew`

Portable orchestration over a bounded Work graph.

Responsibilities include:

- Crew plan parsing/validation;
- dependency ordering;
- workspace acquisition/handoff;
- provider selection;
- Attempt lifecycle events;
- Guard integration;
- workspace change enforcement;
- durable mission receipts;
- retained workspaces until explicit cleanup.

Current Crew v0 is intentionally single-attempt and sequential.

### `guard`

Deterministic Guard policy and native tool mediation contracts.

Use this module to evaluate structured tool effects against contract-bound authority and to create the mediation callback supplied to compatible worker providers.

### `contract-bound-authority`

Derives and checks authority boundaries from Work contracts and resource scope. Keep authority interpretation centralized here rather than reimplementing it in individual adapters.

### `verify`

Independent exact-target verification.

Concepts include:

- verifier catalog/provider;
- verification plan;
- verification engine;
- exact target identity;
- criterion/evidence coverage;
- negative controls;
- receipts and result events.

Verification does not perform organizational acceptance.

### `context`

Deterministic `ContextPack` composition and edits with measurable token budgets and stable fragment markers.

Context sources may be supplied by higher-level integrations. The portable composer itself remains independent of a specific repository or organization.

### `rules`

Portable Rule schema, catalog, deterministic selection, binding modes, and conversion into Context inputs.

Organization-specific Rule contents belong outside the portable core.

### `router`

Evidence-based deterministic routing among eligible workers/strategies.

Current policy forms include cheapest-capable, fastest-capable, highest-confidence, and balanced routing.

Routing cannot bypass Work authority or verification requirements.

### `refiner`

Evidence-to-learning proposal lifecycle. Refiner produces reviewable promotion candidates rather than silently changing permanent policy.

### `operator`

The operator loop over one Work stream, with no host dependency:

- `summarizeOperatorWork` and `summarizeOperatorWorks` give status, next action, and metrics. The
  metrics are attempts, repairs, recovery, estimated cost, and human interventions per accepted
  outcome.
- `recordOperatorReview` records an independent review.
- `acceptOperatorWork` records a human Board acceptance, then runs Refiner analysis and derives Router
  evidence.
- `closeOrphanedAttempts` handles resume recovery.

Every write is projected through the Board before it is appended, so a refused decision never reaches
the Ledger.

### `integration`

Work-level integration control, Attempt leases, parking/release behavior, and durable integration checkpoints.

The Integration Controller operates on the existing Work stream. It does not own a second Board.

### `benchmark`

Benchmark schemas and instrumentation for comparing Harness behavior against baselines using independently verified outcomes and human interventions.

### `sandbox`

Portable containment/proof contracts used by concrete sandbox implementations.

### `disposable`

Disposable derivative lifecycle for proof operations that must perturb or inspect a candidate without contaminating the canonical artifact.

### `workspace-digest`

Artifact/workspace identity utilities used to bind proof to exact bytes and detect drift.

## Adapter entry points

### `/codex`

Exports the Codex App Server Host/worker adapter used by the real canary and repository Work runner.

Use when Codex is the concrete execution product. Keep Codex-specific request/transport behavior below this adapter.

### `/dsh`

Exports the DeepSeek Harness adapter and related host integration types.

DSH is a concrete Host. Portable application code should normally depend on root interfaces, not DSH types.

### `/dsh-products`

Exports DSH product worker route composition used for direct Codex/Claude product routes through DSH.

### `/git-worktrees`

Exports the Git workspace implementation and candidate/checkpoint helpers.

Current responsibilities include:

- `GitWorktreeWorkspaceProvider`;
- candidate path-scope derivation;
- candidate preservation;
- verified-candidate promotion;
- Git-backed checkpoint mechanics.

### `/local-verify`

Exports the local command verifier implementation for deterministic read-only command checks.

### `/durable-ledger`

Exports `DurableEventLedger`, the current local file-backed hash-chained Ledger.

`readDurableLedgerEvents(directory)` reads a Ledger's committed events without taking the writer
lock. It verifies the hash chain and never writes. `readRepositoryWorkLedgers(gitCommonDir)` (local
adapter `work-ledgers`) discovers every repository Work Ledger and reports unreadable ones
separately.

Typical use:

```ts
import { DurableEventLedger } from "@werhiz/rhiz-harness/durable-ledger";

const ledger = await DurableEventLedger.open({
  directory: ".rhiz/ledger",
  ledgerId: "ledger:example",
});

try {
  // append/replay/integrity work
} finally {
  await ledger.close();
}
```

## Typical programmatic composition

A current end-to-end composition looks like:

```ts
const ledger = await DurableEventLedger.open(...);
const workspaceProvider = new GitWorktreeWorkspaceProvider(...);
const host = new CodexAppServerHost(...);

const workers = new WorkerCatalog();
workers.registerHost(host);

const run = await new CrewSupervisor({
  plan,
  ledger,
  workerCatalog: workers,
  workspaceProvider,
  actor,
}).run();

// Capture exact candidate identity.
// Independently verify it with VerificationEngine.
// Record an integration checkpoint.
// Keep acceptance separate.
```

See `scripts/run-repository-work.mjs` for the canonical current executable composition.

## Parsing at boundaries

Zod schemas are part of the product contract. Validate:

- external JSON;
- adapter responses;
- event payloads;
- provider observations/results;
- Work contracts;
- verification plans;
- Rule catalogs;
- Guard records.

Do not cast unknown values into portable types at a trust boundary.

## Error handling

Most modules fail closed when a required safety fact is absent or inconsistent. Examples include:

- invalid workspace binding;
- duplicate worker identity;
- unclassified provider capability;
- write-scope escape;
- verification target drift;
- duplicate Ledger event id;
- Ledger integrity failure;
- unsupported Work/provider combination.

Callers should preserve typed errors and relevant evidence rather than converting every failure into an undifferentiated worker retry.

## API stability

Before public `1.0`, use these principles:

- Constitution-level semantics should change rarely and explicitly.
- Portable contract changes require migration thought even during pre-alpha.
- Adapter internals may evolve more quickly than portable Work meaning.
- New provider features should enter through capability discovery rather than hidden assumptions.
- Removed or renamed canonical concepts should be reconciled across schemas, docs, events, tests, and UI in one change.

## Generated reference direction

For public release, the package should publish generated TypeScript API documentation from the same declarations consumers install. Generated reference should complement this conceptual map, not replace architecture and operator documentation.
